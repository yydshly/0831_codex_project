# BotVod Capability Lab：交付契约

## 设计契约

| 字段 | 决策 |
| --- | --- |
| Entry mode | Revision-led refinement（基于已交付 Capability Lab） |
| Request revision | 3 |
| Target user and context | 希望快速理解 BotVod 产品能力、真实效果、技术链路与可扩展价值的产品经理、开发者、内容创作者和运营人员 |
| Desired first impression | 先用三句话回答“它如何定位、怎样找源、播放/下载是不是核心”，再允许用户深入证据与演示 |
| Visual ambition | Editorial |
| Experience architecture | Editorial Flow |
| Visual constraints | 使用“研究台 / 数据链路”语义；固定深色主题；不复制 BotVod 页面，不使用第三方图片、字体或品牌资产；信息层级优先于装饰 |
| Information constraints | 严格区分官网宣称、公开接口观察、本项目模拟和技术推断；明确区分“公网内容搜索”“站内缓存检索”“已知 URL 的媒体源解析”；所有时效性结论标注观察日期 |
| Operation constraints | 纯静态前端；不调用 BotVod 下载接口；不抓取第三方媒体；不接收 Cookie；用户输入仅在本机内存中进行平台识别和模拟 |
| State constraints | 默认、解析中、解析成功、缓存命中、队列处理、完成、无效链接和重置状态均需有明确反馈；结果不可伪装成真实下载 |
| Environment constraints | 独立 Vite + TypeScript 应用；支持相对资源路径与 GitHub Pages 子路径；中文单语言；固定深色主题；桌面、平板与 390px 手机可用 |
| Primary journey | 首屏读到核心定位 → 比较三种“搜索”并确认 BotVod 的真实边界 → 沿找源流程理解难点 → 判断播放/下载只是交付层 → 在媒体系统全景中区分 BotVod、我们的适配层、MediaCMS 与 CDN → 再用本地演示验证缓存/队列分支 |
| User-defined phases | 第一：产品定位与关键点；第二：是否属于视频在线搜索下载、如何搜索源；第三：找到可下载源后，在线播放与下载的技术地位；第四：将 MediaCMS 的存储、处理、管理、分发、展示能力纳入后期理解；网页整理、README 摘要与 GitHub 部署 |
| Required artifacts | 研究 README、媒体平台全景笔记、技术原理笔记、交付契约、可运行 Demo、Demo README、验证记录、根索引更新、GitHub Pages 配置与在线页面 |
| Autonomy authorization | 用户明确要求将后期理解汇总进网页、更新外层 README、提交 GitHub 并部署；允许在现有仓库与 GitHub Pages 约定内直接实现、验证、提交和推送 |
| User-decision boundary | 仍不接入真实下载、账号登录、Cookie、后端服务或第三方媒体文件；不代替用户决定商业许可与合规政策 |
| Observable completion criteria | 原有三项核心判断保持清晰；新增章节用一句话和系统地图区分 BotVod、我们的适配层、MediaCMS 与 CDN；明确 MediaCMS 覆盖接入后存储、处理、管理、站内搜索、源站分发与门户展示，但不负责任意网页搜源；外层 README 首屏提供一句话理解；原有演示继续覆盖缓存命中与队列两条路径；键盘可完成主流程；1440px、768px、390px 无横向溢出；reduced-motion 不丢信息；`npm run check` 与 `npm run build` 通过；GitHub Pages 工作流包含该 Demo，推送后在线地址可访问 |

## 设计方向

| 决策 | 选择 | 为什么服务目标 | 可观察约束 | 验收标准 |
| --- | --- | --- | --- | --- |
| 信息层级 | 首屏先给出一句判断和可操作演示，研究证据随后展开 | 用户先理解结果，再决定深入到原理或边界 | 首屏不堆叠全部研究结论 | 首次扫描能回答“是什么、怎么试、是否是真实下载” |
| 演示模型 | 一条可见状态机驱动格式、架构节点和日志 | 同一状态源让能力与原理形成闭环 | 不使用随机结果；两条分支可重复复现 | 重置后同一预设得到同一结果 |
| 真实性表达 | 使用“公开观察 / 本地模拟 / 扩展建议”三类徽标 | 防止将模拟能力误认成站点保证 | 关键结论附近必须出现来源层级 | 用户能区分已观察事实与推演 |
| 字体角色 | 大标题、章节标题、正文、等宽数据四级 | 支持长中文阅读与技术日志 | 不依赖远程字体；正文行长受控 | 390px 下标题和标签不截断 |
| 色彩与材质 | 墨黑蓝背景、冷白正文、酸橙绿状态、琥珀风险 | 建立研究台语义并区分成功与警示 | 色彩不是唯一状态表达；边框/文本同步变化 | 默认、运行、完成、风险均可辨识 |
| 动效 | 仅用于状态推进、节点高亮和进度反馈 | 解释数据流而非制造装饰 | 遵守 `prefers-reduced-motion` | 降低动效后所有状态即时可读 |
| 响应式 | 桌面演示台双栏，窄屏单列；导航可横向滚动 | 保持文档流和主流程连续 | 无固定侧栏、无依赖悬停的关键操作 | 390px 可完成链接演示与路线筛选 |

## Revision 2：方向修订

| 对比层 | 继续保留 | 本轮差距 | 最小完整改造 | 验收标准 |
| --- | --- | --- | --- | --- |
| 构图 | 深色研究台、编辑型长页、交互演示 | 三个核心问题埋在后续章节，首屏不能立即形成判断 | 在 Hero 后新增“核心技术判断”主章节，并把导航第一入口指向它 | 1440px 与 390px 首轮阅读均先看到三项结论 |
| 信息层级 | 先结论、后演示、再证据 | “搜索”一词未拆分，容易误解为公网视频搜索引擎 | 增加公网搜索、站内缓存检索、URL 找源三列对照 | 不阅读长文也能判断 BotVod 只有后两种能力 |
| 原理表达 | 现有端到端架构图与状态机 | 找源内部步骤过于概括，播放/下载与找源的难度关系不够清楚 | 增加来源解析流程与价值/难度分层 | 找源步骤、事实层级与交付层边界同时可见 |
| 风险边界 | Cookie、版权、透明度风险 | “找到源就不是问题”可能掩盖签名过期、分片、A/V 合并等交付约束 | 增加“更简单但不是零问题”工程清单 | 结论既认同用户判断，又明确残余工程工作 |
| 响应式 | 原有 1440/768/390 断点 | 新增图表可能造成窄屏溢出 | 桌面分栏、移动端纵向流；无横向滚动依赖 | 三尺寸无内容裁切，阅读顺序一致 |

## Revision 3：媒体系统全景与 GitHub 发布

| 对比层 | 继续保留 | 本轮差距 | 最小完整改造 | 验收标准 |
| --- | --- | --- | --- | --- |
| 核心判断 | BotVod 是 URL 驱动的媒体摄取服务 | 后续讨论中的 MediaCMS 结论尚未进入网页 | 新增一句话系统结论，明确两者处于媒体链路的上下游 | 不阅读长文也能说出 BotVod 与 MediaCMS 的职责差异 |
| 系统边界 | 找源、缓存、交付三层关系 | “存储和分发展示”与“搜源下载”仍可能被混为一类 | 增加 BotVod、我方平台、MediaCMS、CDN 四类系统对照 | 每一层都有输入、职责、输出和不负责事项 |
| 产品路线 | 统一 Manifest、私有缓存、任务治理 | 还没有把持续扩源与下游资产门户连成完整产品 | 增加 Source Adapter → Policy → Asset CMS → CDN 的组合架构 | 页面能直接指导后续平台边界与建设顺序 |
| 文档入口 | 研究 README、Demo README、根索引 | 外部读者缺少一句话摘要和在线入口 | 三层 README 与 Pages 首页同步摘要、边界和在线链接 | GitHub 仓库首页一眼可见一句话理解与 Demo 地址 |
| 部署 | 现有 Pages 只构建 early.tools Demo | BotVod Demo 尚未进入 Pages artifact | 扩展工作流构建并发布 BotVod 子路径 | 线上子路径返回 200 且内容包含媒体系统全景 |
