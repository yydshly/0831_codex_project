# 架构与运行链路

## 系统分层

Microduck 的关键价值在于同时公开了训练侧和产品运行侧，可以把系统拆成四层：

```text
┌─────────────────────────────────────────────────────────┐
│ 高层交互：手柄 / BLE / 网络 API / 未来自主行为          │
└───────────────────────┬─────────────────────────────────┘
                        ↓ 意图与命令
┌─────────────────────────────────────────────────────────┐
│ 实机运行时 microduck：robotd、设备服务、安全、OTA        │
└───────────────────────┬─────────────────────────────────┘
                        ↓ 61D 观测 / 14D 动作
┌─────────────────────────────────────────────────────────┐
│ ONNX 运动策略：walk、stand、kick、pick、roller...        │
└───────────────────────┬─────────────────────────────────┘
                        ↓ 关节目标
┌─────────────────────────────────────────────────────────┐
│ 硬件：15 个电机、IMU、摄像头、ToF、音频、电池与主控      │
└─────────────────────────────────────────────────────────┘

训练侧 microduck_rl：机器人模型 → MuJoCo/mjlab → PPO → ONNX
```

`microduck_rl` 不直接成为机器人固件；它生产运行时消费的策略产物。`microduck` 也不负责重新训练，而是保证策略在真实设备上的输入、时序、输出和故障边界。

## `microduck_rl`：训练平面

训练仓库主要由以下概念构成：

- 机器人模型、关节顺序、默认姿态和碰撞配置；
- 不同运动任务的环境配置、命令生成器、观测、奖励和终止条件；
- mjlab/MuJoCo Warp 并行仿真；
- `rsl_rl` PPO Actor-Critic 训练；
- BAM 电机与摩擦模型、域随机化和扰动；
- checkpoint 评估、play 和 ONNX 导出。

Actor 和 Critic 不一定看见完全相同的信息。部分任务允许 Critic 使用训练时特权信息，而 Actor 只使用实机可获得的观测。例如踢球策略可在训练时让 Critic 知道球的位置，但部署 Actor 并不因此自动获得视觉追踪能力。

## `microduck`：运行与产品平面

实机软件的中心是 `robotd`：它汇聚传感器与外部命令，在固定控制周期内构造策略观测、执行 ONNX、处理动作并驱动电机。外围服务则覆盖：

- 电机总线和设备发现；
- IMU、ToF、摄像头、音频等传感器/媒体；
- 手柄、BLE 与本地网络控制；
- 视频流和设备 API；
- 配置、日志、健康状态和人工恢复；
- 签名 OTA、健康门禁和失败回滚。

这说明运动策略只是产品栈中的一个可替换组件。任何自定义策略都必须服从运行时的时序、安全和设备状态机。

## 50 Hz 控制闭环

可将单次控制周期理解为：

```text
读取电机编码器和 IMU
        ↓
生成关节位置/速度、角速度、重力方向等观测
        ↓
合并速度、头部和身体姿态命令
        ↓
按训练约定排序、缩放和归一化
        ↓
ONNX Actor 推理得到 14D 动作
        ↓
home pose + action scale × action
        ↓
滤波、限幅、安全状态与控制增益
        ↓
发送关节目标并记录健康/遥测
```

50 Hz 的意义不只是性能指标。训练中的控制步长、动作保持、延迟模型和实机调度频率必须一致或在随机化范围内，否则策略可能在数学接口相同的情况下出现行为漂移。

## 策略 ABI

多个动作策略共享同一 `61 → 14` 形状，形成了近似的策略 ABI，但完整 ABI 至少还包括：

- 14 个受控关节的名称、顺序和正方向；
- home pose 与关节零位；
- 观测缩放、裁剪、历史量和归一化统计；
- 命令 13D 的字段顺序、单位和范围；
- 动作缩放、滤波、控制增益和限幅；
- 控制周期、推理精度与失帧处理；
- 策略适用姿态、进入条件和退出条件。

因此，仅检查 ONNX 的输入输出维度不能证明模型安全兼容。扩展策略系统时，应把上述字段写入可机读 manifest，并在加载前校验。

## 设计启示

1. 将训练、模型产物和运行时拆开，能让研究迭代不直接污染产品生命周期。
2. 固定策略 ABI 适合技能热切换，但必须同时版本化隐式参数。
3. 高层智能体应发“意图”，低层策略负责稳定控制；两层之间需要进入条件、完成条件、超时和故障语义。
4. 相机、ToF 和音频服务与运动控制解耦，有利于实时性和故障隔离；需要自主能力时再通过高层状态估计闭环。
