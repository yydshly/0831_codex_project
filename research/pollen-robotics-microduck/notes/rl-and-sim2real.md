# 强化学习与 Sim2Real

## 策略接口

固定研究基线中，典型运动策略使用 61 维 Actor 观测和 14 维动作：

| 观测组 | 维数 | 含义 |
| --- | ---: | --- |
| Base angular velocity | 3 | 机身角速度 |
| Projected gravity | 3 | 机身坐标系中的重力方向 |
| Joint position | 14 | 相对参考姿态的关节位置 |
| Joint velocity | 14 | 关节速度 |
| Last action | 14 | 上一个控制周期的策略动作 |
| Commands | 13 | 速度/转动 3 + 头部姿态 4 + 身体姿态 6 |
| 合计 | **61** | — |

Actor 网络为 `512 → 256 → 128` 的多层感知机，使用 ELU，输出 14 个关节位置偏移。训练由 `rsl_rl` 的 PPO 管线完成，导出脚本把观测 normalizer 与网络一起输出到 ONNX。

这套结构值得研究的原因不是网络新颖，而是它把“机器人可测状态、用户命令和历史动作”压成一个稳定接口，允许多个技能共享部署管线。

## 奖励设计

运动任务通常同时包含：

- 任务奖励：速度/方向跟踪、姿态命令、目标动作完成；
- 稳定性：躯干朝向、脚接触、摆动时间、足部高度；
- 平滑与能耗：动作变化、关节速度/加速度、扭矩、功率；
- 安全与形态：关节限位、碰撞、离地、跌倒和不期望接触；
- 风格约束：头部、身体、步态、滚轮或踢球动作的特定几何关系。

奖励函数的真正难点是多目标权衡。某个策略“在仿真中得分高”不意味着它对电机友好、动作自然或能在电池电压变化下稳定。研究时应同时看 reward term、权重、终止条件和 curriculum，而不是只看 PPO 参数。

## 执行器建模

理想关节常被简化为“给目标位置就立即产生所需扭矩”，真实廉价舵机则受到电源、速度、摩擦、温度和机械间隙影响。项目通过 BAM 相关模型把这些误差放进仿真：

- 电机供电电压与电池压降；
- 转速相关的反电动势；
- 库仑摩擦、Stribeck 区域和负载相关摩擦；
- 电枢/转动惯量与扭矩限制；
- 控制命令延迟；
- 舵机间隙与编码器反馈关系。

其价值在于：策略训练时就经历“控制目标没有被完美执行”的世界，而不是部署后才第一次遇到。

## 域随机化

固定配置覆盖的主要随机变量包括：

| 类别 | 随机化对象 | 主要目的 |
| --- | --- | --- |
| 动力 | 电压、压降、摩擦、armature | 覆盖电池与舵机个体差异 |
| 时序 | 命令/动作延迟 | 覆盖总线、调度和推理抖动 |
| 刚体 | 质量、惯量、质心 | 覆盖装配和模型误差 |
| 接触 | 地面摩擦、外部推力 | 覆盖不同表面与扰动 |
| 传感 | IMU 对齐、编码器偏置和噪声 | 覆盖标定误差和测量噪声 |
| 机械 | 约 `±1°` 舵机回差变体 | 覆盖齿隙和方向切换死区 |

域随机化不是越宽越好。范围过窄会过拟合仿真，过宽会让策略保守甚至学不到任务。更可靠的做法是用实机日志和系统辨识给随机化范围提供数据依据。

## 非对称 Actor-Critic

训练时 Critic 可以接收实机不可直接获得的特权状态，以提高价值估计；部署时只保留 Actor。例如球的位置可以帮助 Critic 判断一次踢球轨迹的结果，但若 Actor 输入中没有球的位置，相机也没有接进观测，那么最终策略仍是依赖初始对准和时序的技能，而不是视觉闭环踢球。

这带来一个通用判断原则：

```text
训练器看见了什么，不等于部署策略看见了什么。
```

评估自主能力时必须查看 Actor 的实际观测，而不能只看仿真画面或训练环境状态。

## ONNX 导出与部署一致性

将 normalizer 打包进 ONNX 是减少漂移的好设计，但仍需共同版本化：

- 观测字段和顺序；
- 关节字段和顺序；
- reference/home pose；
- action scale 与 clip；
- command range；
- policy control timestep；
- 运行时滤波与 PD 增益；
- 模型所需初始状态和切换条件。

建议为每个策略生成 manifest 和黄金向量测试：同一组原始观测在训练 Python 和实机 Rust 中必须产生一致的归一化输入、ONNX 输出和最终关节目标。

## 最值得复用的方法

1. 先测真实执行器，再决定仿真复杂度和随机化范围。
2. 用 Actor 可获得的观测定义真实能力边界。
3. 把策略部署接口当作版本化协议，而不是一个孤立 `.onnx` 文件。
4. 同时评估任务成功、稳定性、电机负担、功耗和恢复能力。
5. 将实机失败日志回流为仿真扰动、奖励调整和回归场景。
