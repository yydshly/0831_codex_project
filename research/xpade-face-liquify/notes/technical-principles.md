# XPADE Face Liquify 技术原理

本文解释 [XPADE Face Liquify](https://xpade.dothome.co.kr/) 在 `2026-08-31` 观测基线下，从图片载入到 PNG 导出的主要数据流。它是[研究入口](../README.md)的技术补充，不是上游源码文档。

## 证据边界

- **已验证事实**：浏览器 `FileReader` 读取图片；Human.js 通过 WebGL 执行单人脸检测；输出 468 个关键点；语义控制点驱动 RBF 位移；显示网格为 `48 × 48`；导出网格为 `96 × 96`；Canvas 通过逐三角形仿射映射重绘。
- **解释性模型**：下文公式用于准确解释这类实现的数学关系；除明确标注外，不声称变量名、核函数或矩阵求解方式与上游源码逐字一致。
- **尚未证明**：完整离线能力、零遥测、所有浏览器的一致性能、检测模型精度、极端图片的资源上限。
- **许可证边界**：上游页面未声明许可证。本文只记录行为、架构和通用数学原理，不复制上游实现代码或素材。

## 总体数据流

```text
File / Blob
  │
  ▼
FileReader ──► 浏览器可解码图像
  │
  ▼
Human.js + WebGL ──► 最多 1 张脸、468 个关键点
  │
  ▼
坐标归一化 ──► 语义区域 / 控制点
  │                       │
  │                 参数、画笔位移
  │                       │
  └──────────────────────►稀疏目标位移
                            │
                            ▼
                     RBF 位移传播
                            │
                 ┌──────────┴──────────┐
                 ▼                     ▼
             48 × 48               96 × 96
             显示网格                导出网格
                 │                     │
                 └──────────┬──────────┘
                            ▼
                  三角形局部仿射重绘
                            │
                            ▼
                      Canvas / PNG
```

这条链路可以拆成“感知、控制、传播、重绘、导出”五层。每一层都可以独立替换，因此 Human.js 不是液化本身；它只为后续几何编辑提供人脸坐标。

## 1. 图片读取与坐标空间

### 已验证机制

页面通过 `FileReader` 读取用户选择的本地图片，再交给浏览器解码。后续至少会涉及三套坐标：

1. **源图坐标**：原始像素宽高，导出时需要回到这一空间。
2. **检测坐标**：Human.js 输入或输出所用的缩放/归一化空间。
3. **显示坐标**：Canvas 在当前视口中的 CSS 尺寸与设备像素尺寸。

如果原图宽高为 \(W_s, H_s\)，显示区域为 \(W_d, H_d\)，不考虑裁切时，一个归一化点 \((u,v)\) 的两个常见映射是：

\[
(x_s,y_s)=(uW_s,vH_s),\qquad (x_d,y_d)=(uW_d,vH_d)
\]

实现必须在高 DPI 缩放、等比适配和可能的留白后保持这些空间一致，否则控制点与实际五官会发生偏移。

### 不能由 FileReader 单独推出的结论

`FileReader` 表明初始文件读取可以在浏览器完成，但它不证明页面不会发出网络请求。若要宣称“图片不上传”或“完全离线”，仍需同时检查：

- 从选择图片到导出的 Network 请求与请求体；
- Human.js 模型、脚本、字体等依赖是否自托管；
- Service Worker、分析脚本、错误上报和远程配置；
- 断网重载后是否仍可完成核心流程。

## 2. Human.js 与 468 个关键点

### 已验证机制

页面使用 Human.js / WebGL 检测最多一张脸，并取得 468 个面部关键点。关键点是离散几何坐标，不是已分割的皮肤、头发或背景蒙版。

关键点提供三类信息：

- 面部轮廓与五官的拓扑参照；
- 语义控制点的初始位置；
- 与脸部尺寸相关的归一化尺度，例如眼距或包围盒大小。

### 为什么需要归一化

直接把“移动 10 像素”应用到不同分辨率或不同脸部大小的照片，视觉强度会不一致。更稳妥的解释模型是让参数强度 \(a\) 乘以脸部尺度 \(S\)：

\[
\Delta_i = a \cdot S \cdot q_i
\]

其中 \(q_i\) 是某个语义控制点的方向和相对权重，\(\Delta_i\) 是它的目标位移。这里描述的是通用归一化原则，不代表上游一定使用这一精确公式。

### 已知边界

- 当前上限是一张脸，双人或多人场景不能获得逐脸独立编辑状态。
- 遮挡、极端侧脸、强透视、低照度和低分辨率可能降低关键点稳定性；这是需要用测试集量化的风险，而非本文已测出的准确率结论。
- 关键点本身不提供背景保护。轮廓附近的位移若直接传播到规则网格，可能把发丝或背景直线一并拉弯。

## 3. 从语义参数到稀疏控制位移

### 语义适配层

用户并不直接操作 468 个点，而是使用“眼睛、鼻子、嘴、脸宽、下颌、下巴”等可理解的参数。系统需要把每个参数映射成一组控制点、方向、强度和影响半径。

可以把一个控制项写成：

\[
C_k=\{(p_i,\Delta_i,r_i,w_i)\}
\]

其中：

- \(p_i\)：源控制点位置；
- \(\Delta_i\)：这个参数施加的目标位移；
- \(r_i\)：局部影响尺度；
- \(w_i\)：左右对称、区域重要性或手动强度等权重。

例如，“脸宽”通常需要让左右轮廓点沿相反方向移动；“下巴高度”主要改变竖直方向；“嘴角”则需要左右独立或成对控制。上述例子解释了语义到几何的关系，不承诺上游使用完全相同的点组。

### 参数叠加

多个语义参数和手动画笔可能同时作用于相邻区域。实现需要定义合成规则：

- 线性累加简单，但大强度时容易过冲；
- 按区域或操作顺序覆盖更可控，却可能产生跳变；
- 对最终位移限幅能降低折叠风险，但会改变参数的线性感受。

上游已验证为语义控制点与局部液化共同驱动网格；精确的冲突优先级仍应通过针对性运行时检查确认。

## 4. RBF：把稀疏位移传播到网格

### 已验证机制

上游使用径向基函数（RBF）风格的位移传播：控制点附近变化更强，距离增大后平滑衰减。它把少量控制位移扩散到规则网格的每个顶点。

一个便于理解的归一化表达是：

\[
d(x)=
\frac{\sum_i w_i\,\phi(\lVert x-p_i\rVert/r_i)\,\Delta_i}
     {\sum_i w_i\,\phi(\lVert x-p_i\rVert/r_i)+\varepsilon}
\]

\[
x'=x+d(x)
\]

其中 \(x\) 是网格顶点，\(p_i\) 是控制点，\(r_i\) 是影响半径，\(\phi\) 是随距离衰减的径向核。该公式用于说明“按距离平滑传播”这一事实；上游的具体核函数和是否归一化未在本研究中固化为事实。

### 为什么适合液化

- 控制数量少，仍能形成连续的密集位移场；
- 每个控制点可有独立半径，便于表达局部和大范围调整；
- 结果可以在规则网格顶点上缓存，随后交给统一的三角形渲染流程。

### 质量风险

- **过度拉伸**：相邻顶点间距突然增大，原始纹理被放大。
- **三角形翻转**：位移过强时目标三角形方向反转，产生折叠或错误采样。
- **边界联动**：缺少保护控制点或蒙版时，影响传播到背景。
- **参数互扰**：多个控制区域重叠，局部位移可能相加过强或相互抵消。

建议用雅可比或三角形有向面积检查折叠，并在轮廓外加入固定锚点、衰减带或分割蒙版。这些是扩展建议，不是已验证的上游功能。

## 5. 规则网格与分辨率分层

### 已验证机制

页面使用两档规则网格：

| 阶段 | 网格 | 设计目标 | 主要代价 |
| --- | --- | --- | --- |
| 交互显示 | `48 × 48` | 降低调参时的位移计算和逐三角形绘制成本 | 局部曲线可能更有折线感 |
| 最终导出 | `96 × 96` | 提高局部形变采样密度并减小可见接缝 | 顶点和三角形数量显著增加，导出更慢 |

不要在未确认“数字表示顶点数还是单元数”前，依据 `48 × 48` 或 `96 × 96` 对三角形数量作精确断言。可以确定的是，网格边长翻倍会让二维单元与绘制工作量近似按平方增长。

### 可扩展策略

- 交互时对源图降采样，导出时回到原尺寸重新计算；
- 仅在控制区域提高网格密度，平坦区域保持稀疏；
- 缓存未受影响区域，避免每次输入都全画布重绘；
- 将位移求值放入 Worker，或将采样改为 GPU shader；
- 对设备能力设定网格、源图尺寸和刷新率的动态上限。

这些策略需要用视觉误差与帧时间共同验收，不能只比较单项耗时。

## 6. 三角形仿射 Canvas 重绘

### 已验证机制

规则网格的每个四边形会被拆成三角形。对于每个三角形，系统知道三个源顶点 \(s_1,s_2,s_3\) 和对应的目标顶点 \(t_1,t_2,t_3\)，并求一个二维仿射映射：

\[
t_j=A s_j+b,\qquad j\in\{1,2,3\}
\]

其中 \(A\) 是 \(2\times2\) 矩阵，\(b\) 是平移。三个不共线点足以确定这六个仿射参数。Canvas 绘制时以目标三角形裁剪，把源图的对应区域通过该变换重采样到目标位置；所有三角形拼合后形成液化结果。

### 为什么不用单个整图变换

单个仿射变换只能表达全局平移、缩放、旋转与剪切，无法同时做到“眼睛变大但鼻子基本不动”。逐三角形映射把连续位移场离散成许多局部近似，因此能表达非刚性形变。

### 常见接缝问题

- 三角形边缘的亚像素舍入可能留下细线；
- 浏览器抗锯齿和纹理采样在高缩放时可能暴露接缝；
- 极瘦或翻转三角形会导致仿射矩阵不稳定；
- 色彩空间、Canvas 缩放与导出编码可能让结果与预览略有差异。

验证时应使用棋盘格、直线背景和高对比轮廓，而不只看自然人像；这些测试图更容易暴露局部不连续。

## 7. 原尺寸 PNG 导出

### 已验证机制

导出阶段使用 `96 × 96` 网格，在源图尺寸空间重新绘制并输出 PNG。它不是把当前 CSS 预览简单截图放大。

原尺寸导出的价值是保留输入图像的像素尺寸，但“尺寸相同”不等于“细节无损”：变形区域仍经历插值与重采样，PNG 只保证编码无损，不能恢复已经拉伸的纹理。

### 资源压力

若原图为 \(W\times H\)，单个 RGBA Canvas 缓冲区通常至少需要近似：

\[
M \approx 4WH\ \text{bytes}
\]

实际峰值还可能包含源图解码、显示 Canvas、导出 Canvas、WebGL 纹理、临时缓冲和 PNG 编码。因此，大图同时执行检测、高密网格重绘与导出时，GPU 和内存压力可能远高于单个缓冲区估算。这是基于架构的风险推断，必须通过设备矩阵实测。

## 8. 性能与架构取舍

可以用下列近似模型理解一次重绘：

\[
T \approx T_{controls}+N_v T_{rbf}+N_t T_{canvas}+T_{composite}
\]

其中 \(N_v\) 是网格顶点规模，\(N_t\) 是三角形规模。若每个顶点遍历所有控制点，RBF 求值还会随控制点数量增长。交互与导出采用不同网格，实质上是在为两种体验建立不同性能预算：

- 交互预算看重输入延迟、连续拖动和稳定帧率；
- 导出预算允许等待，但需要进度、取消、内存保护和确定性结果。

Human.js 的 WebGL 检测通常只需在载入或重新选脸时执行；若每次滑杆变化都重新检测，会浪费计算。将“检测状态”和“编辑状态”解耦，是这一类产品可复用的架构原则。

## 9. 可替换模块与扩展接口

| 当前职责 | 可替换或新增方向 | 必须守住的接口 |
| --- | --- | --- |
| Human.js 单脸关键点 | 其他浏览器端 face mesh、多脸检测、用户选脸 | 输出稳定的点索引、置信度、坐标变换和脸部 ID |
| 固定语义控制组 | 自定义预设、左右独立、表情保护 | 参数到控制点位移必须可重复、可撤销 |
| RBF 位移场 | MLS、B-spline、ARAP、GPU displacement map | 位移连续、边界可控、能检测折叠 |
| 规则网格 | 自适应三角网格、局部细分、多分辨率 | 源/目标拓扑对应关系稳定 |
| Canvas 2D 三角形绘制 | OffscreenCanvas、WebGL/WebGPU shader | 预览与导出的坐标和采样规则一致 |
| 单次 PNG | 会话文件、多格式、批量导出 | 保留原图、参数历史、版本和隐私边界 |

## 验证清单

### 功能与错误恢复

- [ ] 清晰正面单人图能得到一张脸及 468 点。
- [ ] 无人脸图有明确错误反馈，不进入错误编辑态。
- [ ] 双人图只处理一张脸，且选择规则可被观察或解释。
- [ ] 每个语义参数只影响预期主区域，重置后与基线一致。
- [ ] 手动推拉、撤销、重做与原图比较状态一致。
- [ ] 导出 PNG 的像素尺寸与源图一致。

### 几何与视觉质量

- [ ] 显示阶段网格为 `48 × 48`，导出阶段为 `96 × 96`。
- [ ] 轻度形变下没有明显三角接缝、裂缝或翻转。
- [ ] 使用直线背景检查轮廓外的非预期弯曲。
- [ ] 使用棋盘格检查位移连续性、局部缩放和采样伪影。
- [ ] 对称参数在对称输入上不产生无理由的左右偏差。
- [ ] 预览和导出的参数结果方向一致，允许的精度差异有记录。

### 隐私与网络

- [ ] 从选择图片到导出完整保存 HAR，并检查图片字节是否进入任何请求。
- [ ] 盘点远程脚本、模型、字体、分析和错误上报依赖。
- [ ] 断网重载后记录哪些功能可用，避免将“本地读取”误写成“完全离线”。
- [ ] 页面明确说明图片处理位置、保存周期和第三方依赖。

### 性能

- [ ] 对 1K、2K、4K 图片记录检测、首次预览和导出耗时。
- [ ] 拖动参数时记录主线程长任务、平均/低分位帧率和输入延迟。
- [ ] 记录 JS 堆、Canvas、解码缓冲和 GPU 纹理的峰值趋势。
- [ ] 低端集显与移动设备有明确的尺寸、网格或刷新率降级。
- [ ] 导出可显示进度，并能在资源不足时安全失败或取消。

### 响应式与可访问性

- [ ] 在 1440 px、768 px、390 px 视口完成载入、编辑、比较、重置和导出。
- [ ] 标签不逐字竖排，面板无不可达的横向溢出。
- [ ] 滑杆、按钮与开关具有键盘焦点、可读名称和非颜色状态提示。
- [ ] 触摸目标尺寸合理，拖动画笔不会与页面滚动产生不可恢复冲突。

## 与能力 Demo 的关系

[XPADE Face Liquify Capability Lab](../../../apps/xpade-face-liquify-lab/) 用原创合成矢量肖像展示语义参数、网格、原图比较与技术步骤。它的目标是让上述数据流可以被操作和讲解，而不是复现上游检测模型或宣称同等图像质量。

因此：

- 可用 Demo 验证信息架构、参数反馈、状态恢复和响应式设计；
- 不可用 Demo 验证 Human.js 准确率、RBF 的上游精确核函数、真实 Canvas 接缝或高分辨率性能；
- 对上游能力的结论仍以 `2026-08-31` 线上页面观测为基线。
